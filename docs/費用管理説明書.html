第1章

全体像 — どのくらいお金がかかるの？

ひとことで言うと

基本料金は0円、電気や水道と同じ「使った分だけ払うしくみ」です。

このシステムは Google のクラウドサービス（Firebase / Google Cloud）の上で動いています。毎月決まった高い利用料（月額数万円など）はかかりません。オープンキャンパスがない月は数円〜数十円、開催する月でも数十円〜数百円に収まるように設計されています。

開催がない月（平時） 数円〜数十円 ほぼ無料枠に収まります。東京の保管庫（Storage）などにわずかに発生。
開催がある月（想定150組） 数十円〜数百円 開催日の読み取り超過分と、当日の高速化（常駐設定）の分が加わります。
予算アラートの基準 月 1,000円 500円・900円・1,000円でメール通知。設計上の上限目安は開催月で $25。

機械を買う必要がないのも大きな節約です。受付用のタブレット・番号表示モニター・紙の発券機は使いません。来場者もスタッフも自分のスマホを使うため、機器の購入費やレンタル費は 0円 です。

第2章

先に覚えておく言葉

請求の画面や技術担当者とのやりとりに出てくる言葉です。むずかしく見えますが、意味はシンプルです。

Blaze（ブレイズ）プラン

Firebase の「使った分だけ払う」料金プランです。無料プランでは一部の機能（自動処理など）が使えないため、このプランに切り替えてあります。

無料枠（むりょうわく）

毎日または毎月、決まった回数・容量までは「0円」で使える枠のことです。このシステムは、ほとんどの項目が無料枠の中に収まるよう作られています。

請求先アカウント

お支払いのクレジットカードを登録してある Google Cloud のお財布です。名前は「Firebase のお支払い」（通貨：日本円 JPY）です。

予算アラート

1か月の利用額が基準（1,000円）の 50%・90%・100% に近づくと、お知らせメールを送る機能です。システムを止める機能ではありません。

東京リージョン

データを置く場所の指定です（英語表記：asia-northeast1）。大学のルールに合わせて、データはすべて日本国内（東京）に置いています。

常駐設定（HOT_INSTANCES）

オープンキャンパス当日だけ、発券と呼出のプログラムを「常に待機状態」にして応答を速くするしくみです。開場30分前に自動でオン、閉場後に自動でオフ（0）へ切り替わり、管理画面の上部で現在の状態を確認できます。

とくに覚えておきたい「費用が増える3つのツボ」

1
常駐設定の自動切替と、終了後の念のための確認

発券（issueTicket）と呼出（callNext）の常駐台数は、定期処理（scheduledTick）が開場30分前に自動で 1、閉場後に自動で 0 へ切り替えます。戻し忘れを防ぐ仕組みですが、閉場後に管理画面上部の表示が「待機オフ（0）」になっているかを念のため確認すると確実です。

2
開催日は Firestore の「読み取り回数」が無料枠に近づく

整理券を持つ来場者（最大約75人）が待ち状況の画面を開いたままにするため、誰かが発券・呼出をするたびに全員の画面へ更新が届きます（150組×4回×75人 ≒ 約4.5万回）。無料枠（5万回/日）を少し超えることがありますが、超過分は10万回あたり数円〜十数円程度のため、正常な開催であれば心配いりません。

3
東京リージョンの画像保管庫（Storage）は 0円にはならない

日本の大学向けにデータを東京（asia-northeast1）へ置いています。東京の Storage は無料枠の対象外のため、画像がわずかでも毎月数円の請求が発生します。「0円ではない＝異常」ではないので安心してください。

第4章

増えすぎないための安全装置

従量課金は「知らないうちに高額請求が来るのでは？」と心配になりがちです。このシステムには、費用が意図せず膨らまないよう、あらかじめ4つの安全装置を組み込んであります。

1
予算アラート（月 1,000円）

1か月の利用額が 500円（50%）・900円（90%）・1,000円（100%） に達すると、登録メールアドレスへ自動で警告メールが届きます。

2
同時起動数の上限（最大 10台）

Cloud Functions には maxInstances: 10 を設定済みです。万一アクセスが集中しても、サーバーが無制限に増え続けて高額課金になることを防ぎます。

3
データの自動お掃除（3重の削除）

閉場1時間後に統計以外のデータ・画像・匿名ユーザーを自動削除します。さらに Firestore の TTL（期限切れ自動削除）と、Artifact Registry の1日削除も有効です。

4
不正アクセスのブロック

入場コード・スタッフコードの連続入力を回数制限（レートリミット）で止め、さらに App Check（reCAPTCHA Enterprise）で不正な外部アクセスを弾く設計です。

!
なぜ「上限を超えたら自動停止」にしていないの？

Google Cloud では予算を超えたら強制的にサービスを止める仕組みも作れますが、あえて設定していません。オープンキャンパス本番の真っ最中に1,000円を超えただけで整理券システムが突然止まると、会場が大混乱するためです。代わりに、500円・900円の段階で早めにメールで気づき、人間が確認して対応する運用にしています。

第5章

ふだんの管理スケジュールと役割分担

費用管理のために特別な毎日作業は不要です。次の5つのタイミングだけ押さえておけば安全に運用できます。

  1. 毎月（月初）
    先月の請求額を1分で確認する 職員
    請求メールまたは管理画面で先月の合計額を見ます。開催がない月なら数円〜数十円です。不自然に高ければ技術担当者へ連絡します。
  2. 開催・リハ前日
    開催前日の確認（匿名ログイン上限） 職員 → 技術担当
    技術担当者に「匿名ログイン上限の引き上げ」を依頼します。常駐設定は開場30分前に自動でオンになるため、手動操作は不要です。
  3. 開催・リハ終了後
    （当日〜翌日）
    管理画面で常駐オフとDB読み取り数を確認する 職員
    閉場後、管理画面の上部で「発券・呼出の常駐」が自動で待機オフ（0）に戻っていることと、「本日のDB読み取り」を確認します。
  4. 開催の 3〜5日後
    開催日の実費を確認・記録する 職員・技術担当
    Google Cloud の請求レポートに開催日の利用額が反映されます。Firestore 読み取りや Functions の金額を見て、想定内（数十〜数百円）か確かめます。
  5. 年度末（年1回）
    カード期限と通知先・引き継ぎを確認する 職員
    登録クレジットカードの有効期限、予算アラートの通知先メールアドレス、運用 Google アカウントの管理者リストを最新に保ちます。

第7章

アラートが届いたとき・困ったとき

予算アラートのメールが届いたときや、請求まわりの困りごとが起きたときの対応です。

「予算の 50%（500円）に達しました」というメールが来た

開催やリハーサルがあった月であれば、一時的な利用増で届くことがあります。まずは落ち着いて第6章の「レポート」で内訳を見てください。

開催がない月に 500円を超えた場合は異常です。すぐに技術担当者へ連絡し、HOT_INSTANCES が 0 に戻っているか確認してもらってください。

「90%（900円）」または「100%（1,000円）」のメールが来た

システムは自動では止まりません。すぐに技術担当者へ連絡し、次の順で原因を切り分けてもらってください。

  1. 常駐設定の確認：issueTicket・callNext の minInstances が 0 か確かめる。

  2. サービス別内訳の確認：請求レポートで急増しているサービス（Firestore / Functions / reCAPTCHA 等）を特定する。

  3. 開催中の場合：管理画面に「発券が急に増えています」の警告が出ていないか確かめ、入場コードの流出が疑われればコードを作り直す。

開催がない月なのに、毎月数円の請求が来ている

正常です。第3章のとおり、東京リージョンの Cloud Storage には無料枠がないため、わずかな利用でも数円ほど請求が発生します。数十円以内であれば問題ありません。

クレジットカードの有効期限が近づいた／カードを変更したい

カードが失効してお支払いが失敗すると、Firebase のプロジェクトが停止し、整理券システムが使えなくなります。Google Cloud お支払い画面の左メニュー「お支払い方法」から、有効期限の1か月前までに新しいカードを登録してください。

担当職員が異動する・退職する

次の3点を引き継いでください。

  • 予算アラートの通知先メールアドレスを、新しい担当者に変更（または追加）する
  • 運用用 Google アカウントへのアクセス方法と2段階認証の引き継ぎ（技術担当者と連携）
  • クレジットカードの請求先名義・経理処理の手順
公開アドレスを大学のドメインに変えたら、費用は増える？

大学がすでに持っているドメインのサブドメイン（例：oc-ticket.〇〇.ac.jp）を割り当てるだけなら、追加費用は 0円 です。通信を暗号化する SSL 証明書も Firebase Hosting が自動で無料発行します。

第8章

守ってほしいこと・連絡先・技術メモ

費用管理で必ず守ってほしいこと

1
開催・リハーサル後は、必ず常駐設定を 0 に戻す

一番よくある課金増加の原因です。イベント終了のチェックリストに組み込み、職員と技術担当者のダブルチェックで戻し忘れを防ぎます。

2
「予算超過で自動停止」は勝手にオンにしない

開催当日にシステムが突然止まるリスクを避けるため、自動停止は設定しない方針です。変更する場合は必ず関係者と相談してください。

3
カード番号・パスワードはこの説明書に書かない

下の控え欄には「担当者名・連絡先・確認場所」だけを書きます。クレジットカード番号やログインパスワードは絶対に書かないでください。

4
このプロジェクト（oc-ticket-2027）に他の用途を混ぜない

他のイベントや別システムを同じプロジェクトに載せると、整理券システムの費用がわからなくなります。専用プロジェクトのまま使います。

  • 現在の常駐設定・DB読み取りの確認：管理画面（/admin）の上部バーに system/runtimeStatus の値（常駐状態と当日 JST の Firestore 読み取り合計）をリアルタイム表示。CLI では gcloud run services list --project oc-ticket-2027 --region asia-northeast1 でも確認可能。
  • Firestore 読み書き件数の確認：Cloud Monitoring の firestore.googleapis.com/document/read_count・write_count、または Firebase コンソールの Firestore「使用状況」で確認。PITR（ポイントインタイムリカバリ）は課金とプライバシー要件の両面から無効のまま維持する。
  • Artifact Registry クリーンアップ：コンテナイメージは1日で自動削除するポリシーを設定済み。デプロイ回数が増えた月に Storage 課金が増えていないか確認する。
  • リクエストログの戻し忘れ防止：調査用に Identity Platform のリクエストログ（monitoring.requestLogging.enabled）を一時有効にした場合は、調査終了後ただちに無効へ戻す。
  • App Check 強制：ENFORCE_APP_CHECK=true とコンソール側での Firestore / Storage 強制を適用しておくと、不正アクセスによる読み書き課金膨張を防げる（負荷テスト時のみ一時解除）。

毎月（月初 1〜5日ごろ）

  • 先月の請求額（請求メールまたはレポート）を確認した
  • 開催がない月なのに数百円以上になっていないか確認した
  • 予算アラートのメールが届いていないか確認した
  • （必要な場合）経理用の PDF 領収書を「取引」から保存した

開催・リハーサルの前後

  • 【前日】匿名ログイン上限の一時引き上げを依頼した
  • 【当日（開場30分前以降）】管理画面で常駐が「常駐中（オン）」になっていることを確認した
  • 【終了後】管理画面で常駐が「待機オフ（0）」に戻っていること・DB読み取り数を確認した
  • 【3〜5日後】請求レポートで開催日の実費を確認・記録した

年度末・担当者交代のとき

  • 登録クレジットカードの有効期限が切れていない（1年以内に切れるなら更新予定を立てた）
  • 予算アラート（月 1,000円）の通知先メールアドレスが最新の担当者になっている
  • 運用用 Google アカウントの管理者権限と2段階認証が引き継がれている
  • 使わなくなった古いテスト用イベントや不要な設定が残っていない
